错误与重试

约 1047 字大约 3 分钟

结果以响应信封里的整数 code 为准：0 成功，非 0 失败。不要按 HTTP 状态码或 msg 文案做程序判断——HTTP 200 也可能是非 0 的 code。

{ "id": "…", "cmd": "req_order", "code": 2004, "msg": "账户可用余额不足", "data": null, "stamp": 1795000001 }

错误码分段

code 段含义处理方式
0成功—
1xxx请求本身有问题：参数、认证、权限、协议版本不可重试，按 msg 修正后重新提交
2xxx业务拒绝：余额、商品状态、订单状态不可重试，修正业务条件或换新单
3xxx冲突或重复：幂等键冲突、重复工单不可重试，先查证原结果
4xxx暂时失败：限流、依赖暂不可用可重试，指数退避
9xxx结果不确定先查证，不要直接重发

以接入清单为准

上面的分段是接入协约，具体错误码在开户时下发的接入清单中给出。未列出的非 0 码按 1xxx 处理，不要自动重试。

常见错误码

code含义处理
1001参数不合法按 msg 修正请求
1002认证失败（签名、时间戳、密钥）检查签名串与系统时间
1003无接口权限在门户为该店铺开通对应权限
1004协议版本不支持升级到受支持版本
2001SKU 不存在或已下架刷新商品目录
2002商品暂停销售停止销售该 SKU
2003数量不满足起订量、上限或步长按目录中的 min_qty / max_qty / step 调整
2004可用余额不足充值或减少数量
2005订单尚未交付等待交付完成后再操作
2006订单不可取消（已交付）走售后
2007订单已终结不要重复操作
2008订单不存在或不属于该店铺检查订单号与店铺
2009订单行不存在核对该订单的实际行号
2010交付引用已过期重新领取交付物
3002幂等键冲突（同键不同内容）检查业务单号生成逻辑
3003重复工单等待已有工单处理完成
4001触发限流按 retry_after 退避
4002服务暂时不可用退避重试
9001结果不确定用查询接口核对，不要重发

HTTP 状态映射

HTTP说明
200业务结果看 code；0 成功，非 0 失败
400 / 422请求不合法，code 通常为 1xxx 或 2xxx
401 / 403认证或权限问题，code 通常为 1002 / 1003
429超过限流，code 为 4001，按 Retry-After 退避
500 / 502 / 503平台侧异常，先看响应体 code；无响应体时按 4002 处理

重试策略

code = 0        → 成功，结束
1xxx / 2xxx / 3xxx → 不重试，修正或查证
4xxx            → 退避重试（1s、2s、4s、8s…，最多 5 次），同 id 同内容
9xxx            → 不重发；用查询接口确认原请求结果

响应头或响应体给出 retry_after（秒）时优先按它等待。

为什么 9xxx 不能直接重发

下单是有资金副作用的命令。超时可能意味着订单已在平台侧受理，换新 id 重发可能导致重复下单与重复扣款。正确做法：

  1. 用 get_order 按 ext_req_id（或已拿到的 order_no）查询。
  2. 查到订单：按订单当前状态继续流程。
  3. 查不到且等待一段时间仍无记录：再用原 id 重试一次。

幂等

命令幂等键说明
req_orderext_req_id（店铺内唯一）同键同内容返回原订单；同键异内容返回 3002
req_cancelorder_no同一订单重复取消幂等
open_caseid同一消息号不重复建单

幂等记录覆盖订单与售后周期，至少 30 天，不随请求缓存过期而消失。

建议的实现方式

  1. 把 code 映射为「成功 / 可重试 / 不可重试 / 待查证」四类（按千位判断即可）。
  2. 下单路径对 9xxx 走查询补偿，绝不直接换新 id 重发。
  3. 记录每次请求的 id、ext_req_id、code 与 stamp，便于与平台对账。
  4. 告警只针对「持续 4xxx」与「大量 9xxx」，避免一次网络抖动就惊动值班。
